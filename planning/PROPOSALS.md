**Context:** the Today experience (`planning/workflow-diagnosis.md`, `planning/today-product-spec.md`, `planning/today-wireframe-spec.md`) cannot show its first primary action — Copy Brief — until a Creative Package already exists for the day's selected Opportunity. Materializing a Creative Package requires executing a Creative Job, and Creative Job execution is deliberately restricted to a trusted runner, never browser code (`src/lib/creative-jobs.ts`'s own comment: "only the trusted runner (never browser code)"). No scheduled mechanism currently invokes that trusted runner anywhere in this repo. Investigating what that execution would actually produce surfaced a second, more important gap: neither existing worker type reaches a real, owner-ready result without either a placeholder result (`mock`), a paid external API call (`product_text_worker` via `run-api`), or a human manually relaying text through Claude (`product_text_worker` via `export`/`import`) — none of which are acceptable for an unattended, zero-cost, pre-arrival step. This proposal closes both gaps together, and only these — it does not touch Today's UI, does not modify the Product Bible, and does not extend past the point where a Creative Package becomes ready.

**Scope discipline:** this app has exactly one proven use case for this kind of state-advancement script (preparing today's Opportunity). Generalizing the name, the scheduling model, or the readiness contract before a second real consumer exists would be speculative architecture — considered during review and explicitly rejected in favor of staying narrow.

**Design Principle:** For every state transition that already has a canonical owner, the preparation script orchestrates only — it must never duplicate business logic already owned by canonical library functions, and must delegate to the existing function responsible for that transition. **The preparation script owns scheduling only for those transitions; it does not own those business decisions** — selection belongs to the selection library, acceptance belongs to the Opportunity library, Creative Job creation belongs to the Creative Job library; this script only decides *when* those things happen. The implementation may end up structured cleanly enough that a more general state-advancement pattern could be extracted later, if a second real use case ever shows up — that's a reasonable side effect of writing it well, not a goal of this proposal. No generic framework, configurable readiness state, or cross-domain orchestration abstraction is introduced here.

**Truthfulness Principle:** this proposal's one piece of new logic is **Creative Package initialization** — establishing the canonical Creative Package for the selected Opportunity using only truthful, deterministic inputs already present on that Opportunity and in Aly & Pon's brand data. It is not a copywriter and not an AI replacement. It must never invent a marketing claim, a statistic, or a framing not already present in the source data. Every field it produces must be traceable back to an existing Opportunity or Brand field. Where this proposal previously said "headline/caption generation," it means this instead: initializing the Creative Package's content honestly, not generating persuasive copy.

**Responsibility:** "Ensure the Opportunity selected for Today has been advanced to a ready Creative Package before the owner arrives — initializing that Creative Package's content truthfully where no content yet exists." A state-advancement operation for every transition that already has a canonical owner, plus one small, bounded, deterministic initialization step where none existed before.

**State handling** (inspects actual current state every run, using the same functions `opportunities-page.tsx` already calls interactively):
| Starting state | Action taken |
|---|---|
| Opportunity status `new` | Accept it (`updateOpportunityStatus(..., "accepted", ...)`), then continue below |
| Opportunity status `accepted`, no Creative Job | Create the Creative Job (`createCreativeJobForAcceptedOpportunity`), then continue below |
| Creative Job absent | Same as above — creation is the missing step |
| Creative Job `queued` | Execute it via the new deterministic Creative Package initializer (not the `mock` executor — see Truthfulness Principle) |
| Creative Job `completed` | No execution needed — proceed to confirm the package |
| Creative Package already present | No-op. Nothing to do; this is success, reported as such |
| Opportunity `dismissed` / `expired` / `converted`, or Creative Job `failed` | Non-actionable — reported as a visible failure/skip, never silently retried forever, never force-advanced |

**Creative Package initialization, concretely:** a new worker type (a plain string constant — `worker_type` is unconstrained `text` in `supabase-add-creative-jobs.sql`, so this needs no migration) paired with one new, small, pure function that composes the Creative Package's initial content directly from the selected Opportunity's own `title`/`reason`/`summary` and Aly & Pon's existing `BrandBible` tone/voice data (`marketing-advisor-context.ts`, already wired into `asset-generation-spec.ts`) — nothing invented, nothing fetched from an API. Registered as one more named entry in the executor map `scripts/creative-workers/runner.ts` already defines for exactly this purpose (`trustedCreativeJobExecutors()`), alongside `mock` and `product_text_worker`, not in place of them. `asset_job_attempts.provider`/`.model` stay `null` for this executor, consistent with the existing convention for every non-real-AI worker (`mock`, `external`). Everything downstream — `buildAssetGenerationSpec`, `renderAssetGenerationBrief`, `creative-package-asset-create.tsx` — consumes this Creative Package exactly as it already consumes any other, unmodified. Separately, `renderAssetGenerationBrief`'s output gains one small, deterministic addition regardless of executor: an explicit instruction not to add text overlays to the generated image unless requested.

**Idempotency is inherited, not reinvented:** `createCreativeJobForAcceptedOpportunity` already returns `{ outcome: "created" | "existing" }` — calling it against an Opportunity that already has a job is already a safe no-op by design. Executing an already-non-`queued` job already fails safely with reason `"not-queued"` via existing claim semantics — treated here as "already done," not an error. `createCreativePackageFromCompletedJob`'s own existing-check makes re-initialization safe too. No raw SQL, no direct table writes; every transition goes through the same guarded library functions the interactive UI already trusts.

**Shared selection contract:** "Choose the first Opportunity" logic must live in exactly one place, imported by both this script and Today's future selection logic — never duplicated. `src/lib/opportunity-review.ts` already defines the canonical ordering (`OPPORTUNITY_LIST_ORDER`: `detected_at desc, created_at desc`) via `listOpportunities(client, "new")`. This proposal adds one small, explicitly named export next to it (e.g. `selectTodaysOpportunity(client)`) that both this script (Node context) and PROP-035's Today view (browser context) import identically — mirroring the precedent `asset-generation-brief.ts` already sets, shared verbatim between the CLI and the browser UI.

**Preserving the trusted-runner boundary:** no browser execution, no new web endpoint or API route, no Vercel Cron, no Supabase webhook or database trigger. Reuses the one scheduled-execution pattern this repo already runs in production — a Windows Scheduled Task invoking a Node script against Supabase, exactly as Daily Advisor already does.

**Operational reliability:** runs once nightly, after Daily Advisor, in the same operating window. Overlap protection reuses Daily Advisor's own concurrency-guard convention (`scripts/daily-advisor/lock.ts`). Machine-asleep/offline risk is inherited from Daily Advisor's already-accepted exposure, not new. A plain `npm run creative-prep` entry provides manual catch-up. Structured output mirrors Daily Advisor's dated-output convention. A missed/failed run surfaces via `STATUS.md`'s blocker pattern and/or Daily Advisor's existing digest channel — no new notification system. No retry/backoff logic needed beyond idempotency plus manual catch-up.

**Known limitation — stuck `running` Creative Jobs are detected and reported, never recovered.** This schema deliberately has no heartbeat, retry-count, or repair mechanism for a Creative Job (confirmed directly: `tests/creative-job-attempts-schema.test.ts` and `tests/asset-job-attempts-schema.test.ts` both assert the migration SQL contains no `repair_stale`/`stale_running`/`heartbeat`/`max_attempts`/`retry_count` construct — a named, deliberate exclusion from an earlier milestone, not an oversight). Without any mitigation, a job abandoned by a crashed trusted-runner process (killed mid-execution, before its own 30-second in-process executor timeout could fire) would stay `running` forever and be silently reported as a benign, successful skip every single night. This proposal adds `CREATIVE_PREP_RUNNING_STALE_AFTER_MS` (5 minutes) as a **reporting-only** threshold: a `running` job younger than that is still reported as a benign skip (exit 0); a `running` job at or past that threshold — or one whose `started_at` is missing or invalid — is reported as `outcome: "failed"` (exit 1), clearly worded as "suspected stale," so an operator is alerted. **The database row is never touched, reset, reclaimed, or retried in any case** — this only changes what the script says it found, never what it does about it. Genuine stale-job recovery (resetting or retrying an abandoned job) remains deliberately deferred to a separate proposal, to be scoped only if real usage ever proves it necessary — building it speculatively now would be exactly the architecture change the schema's own tests document as out of scope for this milestone.

**Explicit stop boundary:** ends the instant a Creative Package exists, with truthfully initialized content, for the selected Opportunity's Creative Job. Asset Job creation, brief rendering, upload, and materialization are untouched — exactly as PROP-027 shipped them, entirely browser-side.
